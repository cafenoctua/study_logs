# bq-job-diagnose コードレビュー

BigQuery のクエリプラン診断ツールをレビューする。このプロジェクト固有の**壊れやすく、壊れても静かに間違った結果を出す箇所**に絞って見る。

詳細な観点は `bq_job_diagnose/REVIEW_GUIDE.md` にある。このスキルはその実行手順。

## レビューの前提

- 指摘には必ず**根拠**を添える（BigQuery 公式ドキュメントの記述、または後述の不変条件 I1-I3 のどれに違反するか）
- 問題点だけでなく**良い点も必ず言及**する。特に「誤用できない設計」になっている箇所
- Learning モードのため、コード変更は**提示のみ**。適用はユーザーの確認後
- **「テストが緑だから良い」で通さない。** このプロジェクトの失敗モードはテストの緑と独立している

## 3 つの不変条件

| # | 不変条件 | 壊れたときに起きること |
|---|---|---|
| I1 | `rules/` は `collect/` を import しない | ルールがデータソースで分岐し、片方の経路でしか正しくない診断が生まれる |
| I2 | `None`（取得不能）と `0`（値がゼロ）を混同しない | RLS 制限ジョブが「0 バイトスキャン」に見え、コスト集計が静かに狂う |
| I3 | CLI は観測事実のみ出力し、提案を書かない | どこまでが検証済みの数字か誰にも分からなくなる |

## 手順

### Step 1: レビューガイドを読む

```bash
cat bq_job_diagnose/REVIEW_GUIDE.md
```

変更範囲を把握する。

```bash
git diff --stat
git diff
```

### Step 2: 機械的チェックを走らせる

```bash
cd bq_job_diagnose

uv run pytest -q                    # 全テスト
uv run ruff check src tests         # lint

# I1: 依存方向（何も出力されないこと）
grep -rnE "^\s*(from|import)\s+(bq_job_diagnose\.)?collect\b|^\s*(from|import)\s+google|requests" \
  src/bq_job_diagnose/rules/

# I2: 黙った既定値（ヒットしたら 1 件ずつ意図を確認）
grep -rn "or 0\b" src/ | grep -v test

# スキーマ変更で静かに壊れる SELECT *（何も出ないこと）
grep -rn "SELECT \*" src/ | grep -vE ":\s*#"   # コメント行を除外
```

結果を報告に含める。**実際に走らせた出力を引用すること**。推測で「通っているはず」と書かない。

### Step 3: 変更内容に応じた観点で読む

変更されたファイルに対応する節を `REVIEW_GUIDE.md` から選んで適用する。

| 変更されたもの | 見る節 | 特に確認すること |
|---|---|---|
| `models.py` | 1.1 | `Stage` に `*_ratio_*` が追加されていないか。`__slots__` 回帰ガードが残っているか |
| `normalize/` | 1.2 | `_as_int()` を通っているか。`None`/`0` の区別 |
| `collect/sql.py` | 1.5 | `creation_time` フィルタ。識別子のバリデーション。SCRIPT 除外の非対称性 |
| `rules/` | 1.3, 1.4, 1.6 | 依存方向。`summary` に提案が混ざっていないか |
| `cost.py` | 1.7 | 2 モデル併記。単価の外出し。`basis_value`/`price_ref` の保持 |
| `report/` | 1.6 | `skipped_rules` が出力されているか |
| テスト | 2 | そのテストは**落ちうるか**。除外セットの性質 |
| `SKILL.md` | 3 | 決定論と非決定論の境界が明記されているか |

### Step 4: テストが落ちうるかを確認する

新規・変更されたテストのうち、**中核的な主張をするもの**（パリティテスト、閾値の境界値テストなど）については、実際に落ちることを確認する。

```bash
# 例: フィクスチャを 1 フィールドだけ意図的に壊す
cp tests/fixtures/sdk_jobs/skewed_join.json /tmp/backup.json
# （値を書き換える）
uv run pytest tests/test_normalize_parity.py -q   # FAIL することを確認
cp /tmp/backup.json tests/fixtures/sdk_jobs/skewed_join.json
uv run pytest -q                                   # 緑に戻ることを確認
```

除外セットが広すぎて何も比較していないテストは、緑でも無価値。

### Step 5: 除外セットの性質を判定する

`SDK_UNAVAILABLE_*_FIELDS` のような除外リストに変更があった場合:

| 種類 | 扱い |
|---|---|
| 構造的に取得不可能（例: `resource_warning` は INFORMATION_SCHEMA 専用列） | 恒久的に正しい除外 |
| **実装していないだけ** | **バグの隠蔽**。実装して除外から外すよう指摘する |

**見分け方**: REST API にそのフィールドが実在するか確認する。実在するなら実装漏れ。

### Step 6: 報告する

以下の構成で報告する。

```
## 機械的チェックの結果
（Step 2 の実際の出力）

## 良い点
（特に「誤用できない設計」になっている箇所）

## 指摘事項
### [重要度] 指摘の要約
- 該当箇所: file:line
- 何が問題か
- 根拠: （不変条件 I1-I3 のどれか / 公式ドキュメントの記述）
- 提案する修正: （コードブロックで提示のみ）

## 判断に迷った点
（あれば。ユーザーの判断を仰ぐ）
```

重要度は「壊れたときに静かに間違った数字が出るか」で決める。クラッシュするバグより、**黙って違う値を返すバグのほうが重い**。

### Step 7: 変更の適用はユーザーの確認後

修正案は提示するだけ。「この変更を適用しますか？」と確認してから実行する。

## 判断に迷ったときの問い

1. この変更で、**同じジョブを別経路で取得したときに違う診断結果**になりうるか？ → なるなら I1 違反
2. この数値が `None` のとき、`0` として扱われる経路はあるか？ → あるなら I2 違反
3. この文章は**観測した事実**か、それとも**推論・提案**か？ → 後者が CLI 側にあれば I3 違反
4. このテストは**落ちうる**か？ → 落ちないなら検証していない
5. この除外は**構造的に不可能**だからか、それとも**まだ実装していない**からか？ → 後者ならバグの隠蔽
